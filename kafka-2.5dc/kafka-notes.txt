OIDC (OpenID Connect) = an identity/authentication layer built on OAuth 2.0. It answers “Who is this user/client?”
OAuth 2.0 = a token/authorisation framework. It answers “Here is a token proving this client has been authenticated/authorised.”
Keycloak = your Identity Provider (IdP). It handles the login/identity side and issues OAuth/OIDC tokens.
MDS (Metadata Service) = Confluent's RBAC/authorisation service. It receives/validates tokens and determines what identities are allowed to do in Kafka.
C3 = the client that needs to authenticate to MDS.

Keycloak = identity provider
OIDC = how C3/MDS integrate with Keycloak
OAuth = the access-token mechanism
MDS = Confluent's RBAC/authorisation layer
Kafka = the resource being protected

The confusing TOKEN listener/callback/JAAS stuff we've been dealing with is Kafka's own internal OAuth machinery needed when RBAC/MDS is enabled. It's separate from the basic concept of C3 authenticating against Keycloak.

| ----------------------- | --------- | ---------------------------------------------------------------- |
| **Keycloak OIDC token** | Keycloak  | Proves **who Alice is**                                          |
| **MDS/Confluent token** | MDS       | Carries the identity into the **Confluent RBAC/security system** |




The important concept is:

Keycloak doesn't know Confluent RBAC.

Keycloak might tell MDS:

username = alice
groups = [Kafka-Developers, Finance]

MDS can then apply the Confluent RBAC model:

Kafka-Developers
    ↓
DeveloperRole
    ↓
READ/WRITE topic orders

The resulting Confluent security context can then be used by Kafka.

And this explains mds-token
